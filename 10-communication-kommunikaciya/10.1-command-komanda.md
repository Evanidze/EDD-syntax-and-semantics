# 10.1 COMMAND (Команда)

## 10.1.1 General structure

**COMMAND** — это конструкция для сопоставления элементов связи EDD с выбранной системой коммуникации. **COMMAND** определяет данные, передаваемые на устройство и считываемые с него.

* Данные для записи на устройство указываются в атрибуте **REQUEST**
* Данные для чтения с устройства указываются в атрибуте **REPLY**
* Определяет различные элементы, необходимые для построения коммуникационного фрейма

{% hint style="info" %}
**Примечание 1:**

* Поле адреса коммуникационного фрейма задается с помощью конструкций: **BLOCK**, **SLOT**, **SUB\_SLOT**, **NUMBER**, **INDEX** (в зависимости от применимости)
* Тип фрейма или его управляющее поле определяется конструкцией **OPERATION**
* Содержимое данных фрейма задается конструкцией **TRANSACTION**
{% endhint %}

{% code title="Lexical structure" overflow="wrap" %}
```c

COMMAND identifier {
    API [integer-constant | reference | integer-expression]<cond>; // не поддерживается в HART
    BLOCK B reference<cond>; // не поддерживается в HART
    HEADER string-value<cond>; // не поддерживается в HART
    INDEX [integer-constant | reference | integer-expression]<cond>; // не поддерживается в HART
    NUMBER integer-constant;
    OPERATION [COMMAND | READ | WRITE];
    RESPONSE_CODES { 
        [referenced-response-codes-specifier | response-codes-specifier] 
    };
    SLOT [integer-constant | reference | integer-expression]<cond>; // не поддерживается в HART
    SUB_SLOT [integer-constant | reference | integer-expression]<cond>; // не поддерживается в HART
    TRANSACTION [integer]? {
        REQUEST { request-item-specifier [, request-item-specifier]* }
        REPLY { reply-item-specifier [, reply-item-specifier]* }
        RESPONSE_CODES { 
            [referenced-response-codes-specifier | response-codes-specifier] 
        }
        POST_RQSTRECEIVE_ACTIONS { actions-specifier }
    }
}
```
{% endcode %}

{% hint style="info" %}
**Примечание 2:** Коды ответов, указанные внутри транзакции, применяются только к этой транзакции.

**Примечание 3:** Коды ответов, указанные вне транзакций, применяются ко всем транзакциям.

**Примечание 4:** Если один и тот же код ответа указан как внутри, так и вне транзакции, приоритет имеет код, указанный внутри транзакции (но только для этой конкретной транзакции).
{% endhint %}

## 10.1.8 OPERATION

**Атрибут OPERATION** определяет действия, выполняемые устройством при получении сервисного запроса от системы связи.

**OPERATION READ**\
Указывает, что основная цель **COMMAND** — чтение данных с устройства. Однако, в зависимости от протокола или механизмов адресации устройства, команда READ может включать данные для передачи на устройство в **REQUEST** (например, переменные **INFO**, **INDEX**) перед получением данных. Эти данные помогают устройству определить, какие элементы следует передать в приложение EDD.

* Для таких **VARIABLES** в **REQUEST** действия **PRE\_WRITE\_ACTIONS/POST\_WRITE\_ACTIONS** не выполняются, так как **OPERATION** имеет тип **READ**.
* Если **POST\_READ\_ACTIONS** завершаются с ошибкой для **VARIABLE**, остальные **VARIABLES** в **REPLY** обрабатываются.

**OPERATION WRITE**\
Указывает, что **COMMAND** записывает данные на устройство. Команда WRITE может включать данные в атрибуте **REPLY**, которые передаются с устройства после записи.

* Для **VARIABLES** в **REPLY** действия **PRE\_READ\_ACTIONS/POST\_READ\_ACTIONS** не выполняются, так как **OPERATION** имеет тип **WRITE**.
* Если **POST\_WRITE\_ACTIONS** завершаются с ошибкой для **VARIABLE**, остальные **VARIABLES** в **REQUEST** обрабатываются.

**OPERATION COMMAND**\
Указывает, что **COMMAND** предназначен для запуска функции.

* **REQUEST** определяет входные параметры.
* **REPLY** определяет выходной параметр.
* Приложение EDD не должно использовать такие **COMMANDS** для передачи данных. Они могут применяться только через встроенные коммуникационные функции в **METHODS**.
* Для **PRE\_READ\_ACTIONS/PRE\_WRITE\_ACTIONS** и **POST\_READ\_ACTIONS/POST\_WRITE\_ACTIONS** переменных такой **COMMAND** обрабатывается аналогично **COMMAND** с **OPERATION WRITE**.

{% code title="Lexical structure" %}
```c
OPERATION [COMMAND | READ | WRITE];
```
{% endcode %}

## 10.1.11 TRANSACTION (Транзакция)

### 10.1.11.1 General structure

**TRANSACTION** определяет поле данных для запросов (request) и ответов (reply) команды.

**Особенности для профиля HART:**

* Можно определить несколько транзакций
* Каждая транзакция маркируется числом после ключевого слова **TRANSACTION** для идентификации
* Если номер не указан, по умолчанию используется **0**
* Каждая **TRANSACTION** может включать набор кодов ответов (**RESPONSE\_CODES**), применяемых только к этой транзакции

{% code title="Lexical structure" %}
```c
TRANSACTION [integer]? {
    REQUEST { 
        request-item-specifier [, request-item-specifier]* 
    }
    REPLY { 
        reply-item-specifier [, reply-item-specifier]* 
    }
    RESPONSE_CODES { 
        [referenced-response-codes-specifier | response-codes-specifier] 
    }
}
```
{% endcode %}

### 10.1.11.2 REPLY

**Атрибут REPLY** содержит список элементов данных, получаемых с устройства.

**Ключевые правила:**

1. Порядок элементов в списке должен соответствовать их расположению в передаваемом **PDU**
2. Если ссылки указывают не на **VARIABLE**, они должны в конечном итоге разрешаться в **VARIABLE**. Запрещены ссылки на:
   * **LIST**, **VALUE\_ARRAY**, **REFERENCE\_ARRAY**, **COLLECTION** с маской элементов (item-mask)

**Особенности работы с данными:**

* Для элементов, не выровненных по границам октетов, необходимо использовать **item-mask** для определения способа извлечения данных
* Даже если младший бит не содержит полезных данных, он должен быть указан в **item-mask** (как "фиктивный" элемент), если за ним следуют другие данные

**Обработка LIST:**\
При ссылке на полный экземпляр **LIST**:

1. Приложение EDD сначала сбрасывает **LIST**
2. Затем заполняет его данными из полученного **PDU**

{% code title="Lexical structure" %}
```c
REPLY { 
    reply-item-specifier [, reply-item-specifier]* 
}
reply-item-specifier := [integer-constant | [reference [<item-mask>]? [INDEX | INFO]? ]]
```
{% endcode %}

**Переменная (VARIABLE)** может иметь одновременно квалификаторы **INDEX** и **INFO**. В этом случае она называется **локальной индексной переменной (local index variable)**.

**Особенности команд с локальными индексами:**

* Ведут себя идентично командам с переменными, квалифицированными только **INDEX**
* Индексные переменные **не хранятся** на устройстве или в приложении EDD

**Дополнительное использование INFO:**\
Может применяться для передачи или чтения **VARIABLE** с единицами измерения, отличающимися от используемых на устройстве.

### 10.1.11.3 REQUEST

**Атрибут REQUEST** содержит список элементов данных, которые отправляются на устройство. Порядок элементов в списке должен сохраняться в соответствующем поле данных передаваемого блока PDU.

Если ссылочные элементы данных не относятся к типу `VARIABLE`, то ссылки внутри элементов EDD должны всегда завершаться как ссылки на `VARIABLE`. Использование других типов элементов EDD не допускается.

**Запрещенные комбинации:**

* `LIST`, `VALUE_ARRAY`, `REFERENCE_ARRAY` и `COLLECTION` с применением маски элементов (`item-mask`).

**Правила упаковки данных:**

* Если элемент данных не выровнен по границам октетов (байтов) в PDU, должна использоваться маска элементов (`item-mask`), определяющая способ упаковки данных в поле.
* Даже если **младший значащий бит** не используется для реальных данных, он должен быть указан в маске (в связке с «фиктивным» элементом данных), если за ним следуют другие элементы.

{% code title="Lexical structure" %}
```c
REQUEST {
    request-item-specifier [, request-item-specifier]*
}

request-item-specifier := [integer-constant | [reference [<item-mask>]? [INDEX | INFO]?]]
```
{% endcode %}

### 10.1.11.4 item-mask

{% tabs %}
{% tab title="1. Основные правила использования масок" %}
Маски элементов требуются **только** когда:

* Переменные (`VARIABLES`) или константы не выровнены по границам байтов.
* Элемент данных начинается или заканчивается в середине байта.

**Стандартное поведение:**

* Элемент **без маски** начинается с бита `0` текущего байта.
* Маски могут применяться к переменным (`VARIABLES`) и константам.

**Формат маски:**

* Биты со значением `1` определяют положение данных в кадре.
  * Должны быть **последовательными** (без разрывов).
  * Если бит `0` маски равен `1`, следующий элемент начинается с бита `0` **следующего байта**.
* Биты, не указанные в маске, считаются равными `0`.
* Перекрытие масок разрешено **только** если бит `0` предыдущей маски установлен в `1`.
{% endtab %}

{% tab title="2. Обработка масок в пакетах" %}
**Ответ (Reply Packet):**

1. Командный битовый поток комбинируется с маской через **побитовое И (`AND`)**.
2. Результат сдвигается вправо на количество **хвостовых `0`** в маске.
3. Соответствующие биты в целевом элементе данных заменяются полученным значением.
4. Остальные биты остаются **неизменными**.

**Запрос (Request Packet):**

1. Данные сдвигаются влево на количество **хвостовых `0`** в маске.
2. Результат комбинируется с маской через **побитовое И (`AND`)**.
3. Полученное значение записывается в текущий активный байт(ы) пакета.
{% endtab %}

{% tab title="3. Семантика битов маски" %}
* Каждый бит маски может иметь смысловую нагрузку.
* **Младший бит (LSB)** маски определяет расположение следующего элемента:
  * `1`: следующий элемент начинается в **новом байте** PDU.
  * `0`: следующий элемент остается в **текущем байте** PDU.

**Для многобайтовых масок:**

* Маска определяет отображение на расширенную область в кадре.
* Количество `1` в маске **не должно превышать** размер элемента данных.

**Особые случаи:**

* Если маска указана для переменной/константы, а соседние элементы **не имеют масок**, то:
  * Первый установленный бит маски — начальная позиция.
  * Последний установленный бит — конечная позиция.
* Маски всегда задаются от **старшего бита (MSB)** к младшему (LSB).
* **Разрывы в маске запрещены.**
{% endtab %}

{% tab title="4. Поддерживаемые протоколы" %}
* **HART** (единственный указанный профиль связи).
{% endtab %}
{% endtabs %}

Пример использования маски данных

{% code title="Lexical structure" %}
```c
REQUEST {
    x <0xF8>, y <0x07>
}
```
{% endcode %}

Поле данных запроса содержит две переменные (VARIABLE), упакованные в один байт. Переменная x упакована в пять старших битов, а переменная y — в три младших бита. Если значение x равно 155, а значение y равно 5, то передаваемый байт будет иметь значение 221 (0xDD).

{% code title="Lexical structure" %}
```c
COMMAND cmd_abc {
    OPERATION WRITE;  // Тип операции: WRITE/READ
    ...               // Атрибуты протокола (SLOT, INDEX и др.)
    TRANSACTION {
        REQUEST { // Для WRITE (для READ используется REPLY)
            a,       // Элемент без обработки
            b <0x3C>, // Битовый маскинг (00111100 в бинарном виде)
            c        // Элемент без обработки
        }
    }
}
```
{% endcode %}

В коде выше переменные a, b и c имеют тип INTEGER(1). В данном случае биты с 0 по 3 переменной b отображаются на биты с 2 по 5 в кадре данных после переменной a. Переменная c начинается с бита 0 следующего байта в кадре данных (см. Рисунок ниже).

### 10.1.11.5 Data item qualifiers

Переменная (VARIABLE), используемая в запросе или ответе, может быть дополнена ключевыми словами **INDEX** и **INFO**.

* Переменная с квалификатором **INDEX** указывает, что она используется в запросе или ответе в качестве индекса массива.
* Переменная с квалификатором **INFO** означает, что данная переменная фактически не хранится в устройстве или приложении EDD, а передаётся исключительно в информационных целях.
* Переменная может иметь оба квалификатора (**INDEX** и **INFO**). В таком случае она служит индексом массива и не сохраняется в устройстве.

#### **Пример использования**

В коде ниже приведён пример EDD, демонстрирующий применение переменной с квалификатором **INFO**.

```c
TRANSACTION {
    REQUEST {
        units (INFO), x, y
    }
    REPLY {
        units, x, y
    }
}
```

VARIABLEs x и y записываются в устройство в единицах измерения, указанных в 'units'. Переменные x и y хранятся в устройстве (в фиксированных единицах), тогда как 'units' не сохраняется. Это позволяет передавать VARIABLE в единицах, отличных от current unit (единиц отображения переменной).

Код ниже демонстрирует использование переменной с указанием индекса.

```c
TRANSACTION {
    REQUEST {
        code (INFO), table[code]
    }
    REPLY {
        code, table[code]
    }
}
```

Элемент данных в массиве **table**, указанный кодом, записывается в устройство. Устройство сохраняет значение кода и возвращает его. Переданный вместе с кодом элемент данных также сохраняется, после чего возвращается значение, хранящееся в устройстве.

В коде ниже показан пример, демонстрирующий использование локального индекса VARIABLEs.

```c
TRANSACTION {
    REQUEST {
        code (INFO, INDEX), table[code]
    }
    REPLY {
        code, table[code]
    }
}
```

Переменная **code** с квалификаторами INFO и INDEX передается на устройство, но не сохраняется ни в устройстве, ни в приложении EDD. Данная переменная используется исключительно в качестве индекса для массива **table**.

### 10.1.11.6 POST\_RQSTRECEIVE\_ACTIONS

**POST\_RQSTRECEIVE\_ACTIONS** поддерживается **только** симуляторами устройств.

Атрибут **POST\_RQSTRECEIVE\_ACTIONS** определяет **METHODs**, которые должны выполняться симулятором устройства:

1. **После** обновления всех значений в разделе **REQUEST**
2. **После** завершения всех связанных **POST\_RQSTUPDATE\_ACTIONS** (если они определены)
3. **Перед** формированием раздела **REPLY**

**Правила выполнения:**

* **METHODS** выполняются **в порядке их объявления**.
* При аварийном завершении **METHOD** последующие методы **не выполняются**.

```c
POST_RQSTRECIEVE_ACTIONS {
    reference<cond> [, reference<cond>]*
}
```
